The rsmack workspace is a stack of nine Cargo crates: five user-facing macros, one facade, the factory that generates them, the toolkit everything shares, and two development-only crates. Understanding the layering explains why a macro author needs both `rsmack-megamac` and `rsmack-utils`.

<FileTree>
	- packages
		- rsmack — facade: every macro behind one feature-gated dependency
		- rsmack-edoc — docs from constants (generated by megamac)
		- rsmack-wrap — field type wrappers (generated by megamac)
		- rsmack-seanum — SeaORM active enums (generated by megamac)
		- rsmack-fs — folder mirroring (generated by megamac)
		- rsmack-megamac — the macro factory itself
		- rsmack-utils — ExecEnv, Logr, entrypoint drivers, fs helpers
		- rsmack-example-macros — living example crate (not published)
		- rsmack-ui-tests — trybuild diagnostic snapshots (not published)
</FileTree>

## The facade

The `rsmack` crate is a re-export shim. Each macro sits behind a feature, and `full` (the default) enables all of them:

<Code lang="toml" code={`[features]
default = ["full"]
full = ["edoc", "wrap", "seanum", "fs", "megamac"]`} />

Depending on `rsmack` gives you every macro through one import surface; depending on the standalone crates (`rsmack-edoc`, `rsmack-wrap`, ...) keeps compile times down when you need one macro.

## Every shipped macro is megamac-generated

The shipped macros do not hand-write their entrypoints. Each crate's `src/lib.rs` contains a declaration like:

<Code lang="rust" code={`megamac!(kind = Attr, name = edoc, doc = "readme");`} />

The entrypoint function, the payload parsing, and the generated documentation all come from the same machinery you use to write your own macros. When the factory improves — richer docs, faster memoization — every shipped macro inherits the improvement.

## Why a macro author needs two dependencies

Proc-macro crates cannot be imported as plain modules, so the code `megamac!` generates must name its dependencies by path. The generated entrypoints call `rsmack_utils::exec::*` drivers and `exec` receives `rsmack_utils::megamac::ExecEnv` — which is why authoring with `megamac` requires a direct `rsmack-utils` dependency alongside `rsmack-megamac`.

## Quality infrastructure

The workspace enforces its posture mechanically: `clippy::pedantic` denied with zero allows, 100% line coverage via `cargo-llvm-cov`, every error path snapshotted with `trybuild`, parsers fuzzed with `cargo fuzz`, criterion benchmarks per macro, `git-cliff` changelogs, and tag-driven releases to crates.io. The [diagnostics philosophy](/explanation/diagnostics-philosophy/) explains the no-panic guarantee behind it.
