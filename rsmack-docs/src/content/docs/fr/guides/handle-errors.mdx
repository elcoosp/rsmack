Les macros qui paniquent produisent des ICE — erreurs internes du compilateur — dans les builds utilisateur. La paire de diagnostics de [`rsmack-utils`](/reference/rsmack-utils/) remplace les paniques par un rapport structuré : les problèmes fatals renvoient un `syn::Error`, les problèmes récupérables sont collectés et vidés ensemble, et chaque message porte le préfixe de votre macro.

## Renvoyer des erreurs fatales avec finish_result

Quand l'expansion ne peut pas continuer, renvoyez un `syn::Error` avec `?` et passez le `Result` à `ExecEnv::finish_result` :

<Code lang="rust" code={`pub fn exec(args: Args, env: &ExecEnv) -> TokenStream {
    env.finish_result(run(args))
}

fn run(args: Args) -> syn::Result<TokenStream> {
    let path = args.path;
    let file = std::fs::read_to_string(&path)
                    .map_err(|e| syn::Error::new(path.span(), format!("Failed to read file \`{path}\`: {e}")))?;
    // ...
    Ok(quote::quote! {})
}`} />

L'erreur est rendue comme un `compile_error!` au span fautif, préfixée `#[your_crate::your_macro]`.

## Collecter les erreurs non fatales avec Logr

Quand un champ cassé ne doit pas cacher les autres, collectez les erreurs avec `Logr::emit_error` et videz à la fin. `ExecEnv` possède déjà un `Logr` ; `env.finish(...)` vide les erreurs collectées comme jetons `compile_error!` ajoutés à une sortie autrement valide :

<Code lang="rust" code={`for field in args.fields {
    if field.ident.is_none() {
                    env.logr.emit_error(field.span(), "Only named fields supported");
    }
}
env.finish(generate_output())`} />

Un élément cassé rapporte **chaque** problème en une seule passe — l'UX que `proc-macro-error2` a inaugurée, sans la dépendance abandonnée.

## Écrire les messages dans le style maison

Le guide de style de l'espace de travail, imposé par les tests d'instantané, garde chaque diagnostic prévisible :

| Règle | Exemple |
| --- | --- |
| Commencer par l'échec | `Failed to read constants file` |
| `Failed to <verb> ...` pour les échecs de lecture/analyse | `Failed to parse macro_impl_src` |
| `Only <thing> supported` pour les contraintes | `Only named struct supported` |
| ``Unsupported `<thing>` `<value>` `` pour les variantes inconnues | ``Unsupported MacroKind `Nope` `` |
| Identifiants et chemins entre backticks | ``Unresolved const ident `NOPE` `` |
| Pas de point final | ...suit la convention rustc |

Chaque message que les macros livrées peuvent émettre est catalogué dans la [référence des messages d'erreur](/reference/error-messages/).

<Aside kind="tip" title="Figez vos diagnostics">
        L'espace de travail épingle chaque sortie rustc avec `trybuild` dans `packages/rsmack-ui-tests`. Copiez le motif : chaque paire `.rs`/`.stderr` dans votre crate fige un diagnostic contre les changements accidentels.
</Aside>

## Ne jamais paniquer

`expect`, `unwrap` et `panic!` sont interdits dans les chemins de code de macro. Une entrée utilisateur arbitraire doit devenir un `compile_error!`, pas un ICE — l'espace de travail fuzze ses parseurs (`fuzz/`) pour tenir cette promesse.
